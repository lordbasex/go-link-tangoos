# ADR 0012 — GlusterFS for multi-node clusters

- Status: Accepted (second stage: TLS, dedicated bricks, brick operations, quotas, snapshots, NFS)
- Context: users who already run replicated storage on plain Linux (GlusterFS replica 3 over LVM bricks, with server and client quorum) want to build and run the same thing from TangoOS: join several NAS boxes, create replicated volumes with their production options, mount them and share them over SMB or NFS, see healing and split-brain at a glance, and keep the traffic between nodes private. Commercial NAS products sell this as a separate high-availability tier; on TangoOS it is an app.
- Decision: GlusterFS (Debian 13 ships 11.1), managed by the agent through typed operations that build the `gluster --mode=script --xml` argv from validated input and parse the XML output — never free text, never `force` on create. `glusterfs-server` is **not** a dependency of the `tangoos` package: it is installed on demand from the Cluster app (31 MB download, 13 packages), like NUT and Docker, so a single-box NAS never runs `glusterd`.
- Security:
  - `glusterd` accepts a `peer probe` from anyone who reaches TCP 24007, with no password. TangoOS therefore loads an nftables table (`inet tango_gluster`) **before** `glusterfs-server` is installed, that rejects the GlusterFS ports (24007, 24008, 49152–60999) and the TangoOS control channel (24010) for everyone except loopback and an allow-list (pool members plus 15-minute invitations). The firewall unit has no `ExecStop` and is `RequiredBy=glusterd`, so it fails closed.
  - **Joining needs a code and a fingerprint comparison** (docs/17 §3.2): the invited node shows a one-time code and its key fingerprint; the joining node proves the code with a MAC bound to the TLS certificate it sees (channel binding), and the user compares the fingerprint on both screens before the invited node receives its certificate. A plain invitation (firewall only) is not enough anymore.
  - **Cluster PKI.** The first node that adds another creates a cluster CA; every member gets a certificate (CN = hostname) and a copy of the CA key, so any member can add the next node. Rejected alternative: a single CA holder (losing that box would freeze the cluster) or per-node CAs cross-trusted (GlusterFS takes one CA list).
  - **TLS** for management (`secure-access`) and I/O (`client.ssl`/`server.ssl` + `auth.ssl-allow` with the members' CNs) is switched for the whole cluster with a controlled stop orchestrated over the control channel (mTLS between tangod instances). Removing a node revokes it through `auth.ssl-allow`, the firewall and the pool; a CRL is pending.
- Bricks: a directory on a TangoOS Btrfs volume (`/volumeN/@gluster/<volume>`), or a **dedicated LV with XFS** (`-i size=512`) in a storage pool mounted at `/srv/gluster/<volume>` — the layout production clusters use — optionally **thin** so GlusterFS snapshots work. Brick forms are a list of regular expressions (`brickForms`); a ZFS dataset form can be added there.
- Consequences:
  - Debian's `glusterd.vol` has `ping-timeout 0`: TangoOS sets 10 s on install and bounds its own status reads with the CLI `--timeout`.
  - The agent cannot load kernel modules: the package loads `dm_thin_pool` at boot (modules-load.d) for thin bricks.
  - Quotas are enforced late and not for root (GlusterFS behaviour); quota and heal commands run in transient units because they need the host network.
  - A restored snapshot leaves the volume on GlusterFS-managed snapshot LVs (`/run/gluster/snaps`); TangoOS accepts that brick form, treats the original LV as an orphan and cleans the snapshot LVs when the volume is deleted.
  - SMB permission groups of cluster shares get fixed GIDs (derived from the name), so ACLs stored in GlusterFS mean the same on every node; user IDs are still per node.
