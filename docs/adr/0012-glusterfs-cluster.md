# ADR 0012 — GlusterFS for multi-node clusters

- Status: Accepted
- Context: users who already run replicated storage on plain Linux (GlusterFS replica 3 over LVM bricks, with server and client quorum) want to build and run the same thing from TangoOS: join several NAS boxes, create replicated volumes with their production options, mount them and share them over SMB, and see healing and split-brain at a glance. Commercial NAS products sell this as a separate high-availability tier; on TangoOS it is an app.
- Decision: GlusterFS (Debian 13 ships 11.1), managed by the agent through typed operations that build the `gluster --mode=script --xml` argv from validated input and parse the XML output — never free text, never `force` on create. `glusterfs-server` is **not** a dependency of the `tangoos` package: it is installed on demand from the Cluster app (31 MB download, 13 packages), like NUT and Docker, so a single-box NAS never runs `glusterd`.
- Security: `glusterd` accepts a `peer probe` from anyone who reaches TCP 24007, with no password. TangoOS therefore loads an nftables table (`inet tango_gluster`) **before** `glusterfs-server` is installed, that rejects the GlusterFS ports (24007, 24008, 49152–60999) for everyone except loopback and an allow-list. The allow-list is the current pool members plus *invitations*: joining needs a confirmation on both sides (the invited node opens itself to the inviter for 15 minutes; the inviter then probes). The firewall unit has no `ExecStop` and is `RequiredBy=glusterd`, so it fails closed.
- Bricks: a directory one level under `/volumeN/@gluster/` on an existing TangoOS Btrfs volume (`/volumeN/@gluster/<volume>`); every node keeps `/volumeN/@gluster` created because `glusterd` creates the brick directory but not its parents. When the LVM pool lands, a brick will be its own LV with XFS (the layout production clusters use); the brick path validator and `BrickPath` are the only places to extend.
- Consequences:
  - Debian's `glusterd.vol` has `ping-timeout 0`: after a hard power-off the dead peer stays "Connected" and every management operation waits for it (120 s). TangoOS sets it to 10 s on install and bounds its own status reads with the CLI `--timeout`.
  - Management and I/O TLS (`/var/lib/glusterd/secure-access`, `client.ssl`/`server.ssl`) are **not** enabled yet: they need a CA shared by all nodes and TangoOS's local CA is per node. Until then, traffic between nodes is plain TCP inside the allow-list. Tracked in docs/17 §6.
  - SMB on a cluster volume uses the same permission groups as any share (`tg-<share>-rw/-ro`), but group IDs are per node: publish a given cluster volume over SMB from one node only.
